## 08:36 · 第一刀：思考强度和 Token 账本

> `在 API 类型与请求体中增加思考强度 output_config & 设置中持久化思考强度 & 输入区在深度思考开启时显示强度选择 & 每条回答末尾显示本轮 Token 消耗`
>
> 补一句：`如果不确定就显示约XXToken`

**耗时 4m 35s，10 个文件，+163 −6。**

Anthropic 格式下控制参数是 `output_config.effort`，原版有好几档，DeepSeek就给了三档 `low / high / max`（API文档有原版映射关系），而且只在深度思考开启时发送。AI设置了持久化到浏览器储存，非法值就回退到 `high`。助手消息里记录本次用的 effort 快照——续写沿用原强度，重新生成按当前设置。

Token 优先用服务端 `usage`（`input + cache_creation + cache_read + output`）。没有 `usage`（中断、导入的历史）就先按字符估——中文约 0.6 token/字，其余约 4 字符/token。然后我补了那句 `如果不确定就显示约XXToken`：**宁可显示"约 1200"，也不要假装精确到个位。**

**坑三：拖到最左，滑块自己跑。** **这句话是我描述得最费劲的一次**——<u>我不懂"锚点计算"</u>，只能说"按钮文字变了，滑条跟着跑，用户关不掉"。

## 15:12 → 15:38 · 五个坑（五）：这次是我救了它

> `滑动条在手机端只能通过点击切换，滑动无响应`

它先按常规思路给滑动条加了“禁止浏览器接管手势”的样式。**没好。**

真正的原因：面板本身是滚动容器。手指横向拖时，浏览器先把手势判给页面滚动并发出“手势取消”事件，拖动被中断，只剩下“点击跳转”生效。

## 16:31 · 206：它踩了缓存最经典的坑

> `[贴了控制台] GET .../static/xxx.webm net::ERR_FAILED`

**2 分 36 秒。**

事情是这样串起来的：视频地址里带 `/static/`，被当成了普通静态资源拦下来；浏览器播视频会发一种"只要其中一段"的请求（叫 `Range` 请求），服务器回的是 206（意思是"只给你一部分"）；而代码里判断"成功"的 `response.ok`，对 206 也算成功，于是就往缓存里塞；但浏览器缓存根本不接受 206 这种"半截"内容，直接报错；错误又被吞掉了，最后离线脚本返回一个失败结果，浏览器就报了 `ERR_FAILED`。

修法：视频这类媒体请求、带 `Range` 的请求，直接放行交给浏览器；只有状态码**严格等于 200**（完整的成功）才写缓存；版本升到 v2。

12 分钟后我补了一刀：

> `isDirectRequest 还是漏。JS 里 fetch() 一个视频，destination 可能是空字符串，也没有 Range 头。`

**46 秒。** 补了一条按文件后缀判断的规则 `/\.(webm|mp4|m4v|mov|ogv|mp3|m4a|aac|ogg|wav|flac)$/i`，版本升到 v3。

## 13:57 · 字体（续）：超时

> `设置字体下载超时与应用`

下午回来第一个问题：选内置字体时因为要下载，切换那一刻客户端就显示"加载失败"。

改成 `PROBE_TIMEOUT` 30 秒，`loadFace` 返回 `loaded | error | pending` 三态——30 秒还没下完只算 pending，不当失败；超时期间保留 `--chat-font-family`（`font-display: swap` 先按系统字体画），`settleLate` 一拿到成功就立即换上。字体加载调用 `face.load()` 只报错、状态却没进 error 时，800ms 后重试，最多 3 次。重试按钮也修了：处于 `error` 状态的字体再 `load()` 只会立刻失败，要重建 `<style>` 拿到一批新的字体对象才真的会重新下载。

限速 500KB/s 实测（11.5MB 的字体）：

```
 3s ~ 30s   var=有  faces=loading  下载中=true  失败=false
32s ~ 48s   var=有  faces=loading  下载中=false 失败=true   ← 30s 到点才提示

## 08:34 · 侧滑：补了事件，没补对地方

> `修复BUG：手机safari侧滑没有完全滑开（没有滑动到底），侧滑菜单不会完全展开，而是卡在那里不再响应侧滑手势。此时点击按钮仍可展开收起侧滑，但使用侧滑手势不再能展开`

这个问题上一轮已经修过一版。当时的表现是画面和实际状态对不上：`Safari`在滑动过程中被拦下页面默认动作后，有时会漏掉“手指抬起”的收尾信号，导致收尾逻辑不执行，手势卡在拖拽中。看起来抽屉已经展开，但内部状态还是关着，遮罩没出来，点空白处没反应；点“收起边栏”时状态本来就是关，也不会触发重画，按钮像没作用。电脑上的浏览器不会漏这个信号，所以桌面上一直测不出来。

上一版补了四件事：手指抬起或触摸被打断时强制收尾；新一次触摸开始前，先把上一次没收拾干净的手势按当前位置收掉；触摸被系统打断时不再一律弹回，而是按当前位置停住；判断“停住后再松手”改用当前时间，不再信事件自带的时间。另外把状态变化改成每次写入都同步画面，哪怕状态早就是关，点一下也能把抽屉收回去。

这就是“补事件”的思路：哪个信号没来，就再挂一个能兜住它的信号。

但我一试，症状变了没消失：拖到一半抽屉冻在中间，之后手势彻底没反应，按钮却还能开合。

第二次诊断说得很直接：在苹果手机浏览器里，只要滑动过程中拦下页面默认滚动，浏览器就可能把后续触摸信号停掉，抽屉于是冻住；等它把这次触摸判成滚动或系统手势后，“手指抬起”的信号也常常不来。上一轮补的抬手兜底只能收尾，救不了中途冻住。

这次改成换信号来源，不再加兜底：手指按下就开始记录；移动时一旦判断是横向侧滑，立刻拦下页面默认滚动，让浏览器不再把它当滚动，也不收回这次触摸；手指抬起就正常结束；触摸被系统打断就按异常结束。纵向滑动在第一次移动时就放手，列表滚动不受影响。鼠标操作保留原来的兜底，桌面调试照旧。上一轮的抬手兜底、自愈、按位置停住、画面位置同步都保留。

验证时模拟手机尺寸的触屏环境连续拖拽，位置变化连贯无中断，最后完全展开；左滑关闭、鼠标拖拽、边界位置、按钮关闭、遮罩关闭、触摸被系统打断、故意不发结束信号的自愈，都通过了。

两次修法的差别不在代码多少，而在承认哪一层错了：第一次是在补漏掉的“手指抬起”，第二次是承认这条路在苹果手机上压根不该走。

它还留了一个后手：真复现的话，就在拖拽期间临时禁止页面滚动，代价是拖的时候列表不能滚。所幸没用上。

然后它反过来问了我三个小问题：选文言要不要顺手把界面字体切成宋体楷体？`appName` 要不要跟着改成"七七改 DeepSeek"？「华夏」这两个字是风格名还是另有意思？

我一个都没答。因为下一步就出事了。

## 21:34 · 四个字打回一条消息

> `Invalid 'messages.0.content': unknown language '文言（华夏）'. Expected '<date>,<weekday>,<location>,<platform>,<language>' … language a supported native language name. (request_id: f6bad92b-…)`

那个字段不是文案，是请求体里的原生语言名，服务端有一份白名单，只认「中文」「English」这类正经国标名。我往里面填了「文言（华夏）」，它连括号一起把整条消息打回。

两分钟后修完：`latestReminderLanguage: '中文'`，加了一行注释说明这个字段受服务端白名单限制。界面文案不受影响，只有发给模型的那一行日期提示受限。

*副作用挺好笑：界面穿着汉服，回答一口白话。*

**同一个东西，一半归我管，一半归它管——界面文案是自由的，请求体是受管的。** 

它给我留了个后门：真想让它张口就说文言，在设置里把 System Prompt 写成"请始终以文言文作答"就行，一行字的事。还特意补了一句"没动你的 System Prompt，也没往请求里塞任何隐藏指令"——这句我挺受用。

我没写。界面端着就够了，回答再端着，读起来太累。

## 23:15 · 提示词翻译

> `systemPrompt 翻成「系统提示词」，文言那边叫「枢机敕令」`

（措辞是我拍的；日志里这条只剩个标题「设置 i18n 翻译目录路径」。）

两个词，改了两行：`zh.ts:223` 和 `wenyan.ts:223`。之前这两处压根没翻，直接把英文 `System Prompt` 摆上台面——梗体版好歹翻成了"人设脚本"。build 18.22 秒，产物同步，`main.e63dba12.js` 里两个新词都在。

然后是这一程最长的一条指令：

> `聊天框里面的也要改：系统提示词在用户按下"保存"后立即修改（目前：修改-保存-更多操作-系统提示词，更改成功。但是我 开启新对话-更多操作-系统提示词，发现之前修改的不见了）.并在发送按钮中示意系统提示词非空`

根因一句话说清了：提示词存了两层，会话私有层和全局默认层。在会话里改只写私有层，新对话读全局层——所以"失忆"。修法是 `setSessionPrompt` 在会话内保存时同时写回全局默认。已有会话各自独立不受影响，之后新建的对话自动带上。

发送按钮那半句也落了地：

- 提示词非空时，发送按钮右上角一个小红点；
- 鼠标悬停显示当前生效的提示词正文（标题 + 内容，长文本限高 160px）；
- 取值优先级：会话页用会话自己的，欢迎页用全局默认。

顺带把 `SystemPromptCard` 里硬编码的 `System Prompt` 也接进翻译，四语言跟着界面切。

它留了个小尾巴问我：对话框那句提示（"从下一条消息开始生效"）没提"新对话也会继承"，文案没跟上新行为，要不要改。我没回，这条到现在还挂着。

**这条 bug 最值钱的不是修法，是我怎么报的。** 我把操作路径一步一步写了出来：修改-保存-更多操作-系统提示词，改成功了；开启新对话-更多操作-系统提示词，不见了。**把复现步骤当咒语念一遍，它就能直接定位到"读的是另一层"，不用猜。**

## 23:37 · 卡

> `优化性能，聊天记录一多就容易卡`

它先说好消息：问题不在"记录太多所以慢"这种玄学，在几个特别勤快的代码——每次滑动都把整棵消息树拉出来重新量一遍身高。

严格按"无感优化"做，四处改动都不碰交互和视觉：

| 文件 | 改动 | 解决什么 |
|---|---|---|
| `src/app/viewport.ts` | 触摸滚动判定改为按下时只测一次可滚动祖先；视口高度变量没变就不写样式 | `touchmove` 不再逐层 `getComputedStyle` + 读 `scrollHeight` 强制重排 |
| `useCurrentMessage.ts` | 逐条测矩形 → 二分查找 | 布局读取从 500 次降到约 9 次 |
| `MessageList.tsx` | ResizeObserver 回调合并成每帧一次 rAF | 窗口变化时不再一帧内反复读写 `scrollTop` |
| `historyNodes.ts` | 160 字预览边扫描边截断 | 长会话更新时不再对每条回答全文做正则替换 |

它还给了一个"更狠"的选项没动：`content-visibility: auto`，只渲染视口附近的消息。效果好得多，但会动到历史跳转和滚动位置的判定——不是无感优化，等我实测完再说。

然后它问了我两个问题：手机真机上侧滑卡，还是桌面浏览器模拟触屏？现在滑动和拖窗口还卡吗？

我回了十个字：

> `手机好了，PC浏览器拖窗口还是卡`

## 23:59 · 这一次的停手，不算本事

00:02，它刚开始查"还有哪些代码在 resize 时火上浇油"。

我取消了。

**PC 拖窗口到今天还卡着。** 这篇记录里这一行，就当欠条。

Safari 那次我停得心安理得：没有真机数据，猜着改只会更糟。这次不一样——它明明能修，是我不想在凌晨三点看它一条一条试。

**两种停手长得很像，区别是：一种是有判断，一种是没耐心。**

## 最后：vibe coding 教我的五件事

我在这 64 小时里学到的，没有一条是关于 React 的。

**一、能把现象描述清楚，比能写代码更稀缺。** 

**二、验收权比实现权重要。** 

**三、"我不知道，但我能看出来不对"，是一种完整的能力。** 

**四、能停手，也是能力。** 

**五、但停手分两种。** 

如果重来一次，我会：**报 bug 时把操作路径一步一步写出来。** 提示词"失忆"那条，我写的是"修改-保存-更多操作-系统提示词，改成功了；开启新对话-更多操作-系统提示词，不见了"。它一眼定位到读的是另一层，不用猜。这不是技巧，是免费的精度。

折腾的乐趣大概就在这里——不是从零造一个，而是把别人搭好的房子，改到自己住着顺手。**只不过这一次，我全程站在门口说"这儿再挪一点"，没有碰过一次砖。**
