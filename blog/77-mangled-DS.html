15:12 → 15:38 · 五个坑（五）：这次是我救了它

滑动条在手机端只能通过点击切换，滑动无响应

它先按常规思路给滑动条加了“禁止浏览器接管手势”的样式。没好。

真正的原因：面板本身是滚动容器。手指横向拖时，浏览器先把手势判给页面滚动并发出“手势取消”事件，拖动被中断，只剩下“点击跳转”生效。

26 分钟后我贴了一份某西方神秘AI的完整分析过去，核心是：你的代码完全依赖浏览器原生滑动条自带的拖动实现，没有自己监听手指移动，也没有按手指坐标计算数值。一旦浏览器不给面子，整个滑条就废了。“禁止浏览器接管手势”只是告诉浏览器怎么处理手势，它不会替你实现拖动。

2m 5s 后它重写了。 手指按下时锁定这个手指的后续事件并按手指横向坐标立即取位，手指移动时持续更新，手指抬起时结束并解除锁定，补上“手势被取消”和“锁定丢失”两种情况的复位。换算用滑块区域的边界位置减去 26px 拇指宽，夹紧到 0~1。数值变化回调只在手势未进行时生效，保留键盘操作，也不让原生跳值覆盖手指位置。

事情是这样串起来的：视频地址里带 /static/，被当成了普通静态资源拦下来；浏览器播视频会发一种"只要其中一段"的请求（叫 Range 请求），服务器回的是 206（意思是"只给你一部分"）；而代码里判断"成功"的 response.ok，对 206 也算成功，于是就往缓存里塞；但浏览器缓存根本不接受 206 这种"半截"内容，直接报错；错误又被吞掉了，最后离线脚本返回一个失败结果，浏览器就报了 ERR_FAILED。

这条 bug 最值钱的不是修法，是我怎么报的。 我把操作路径一步一步写了出来：修改-保存-更多操作-系统提示词，改成功了；开启新对话-更多操作-系统提示词，不见了。把复现步骤当咒语念一遍，它就能直接定位到"读的是另一层"，不用猜。

23:37 · 卡

优化性能，聊天记录一多就容易卡

它先说好消息：问题不在"记录太多所以慢"这种玄学，在几个特别勤快的代码——每次滑动都把整棵消息树拉出来重新量一遍身高。

严格按"无感优化"做，四处改动都不碰交互和视觉：

文件改动解决什么
src/app/viewport.ts触摸滚动判定改为按下时只测一次可滚动祖先；视口高度变量没变就不写样式touchmove 不再逐层 getComputedStyle + 读 scrollHeight 强制重排

它还给了一个"更狠"的选项没动：content-visibility: auto，只渲染视口附近的消息。效果好得多，但会动到历史跳转和滚动位置的判定——不是无感优化，等我实测完再说。

然后它问了我两个问题：手机真机上侧滑卡，还是桌面浏览器模拟触屏？现在滑动和拖窗口还卡吗？

我回了十个字：

手机好了，说明第一刀砍对了。PC 拖窗口是另一回事：那个场景里浏览器每一帧都要重排整棵消息树，500 条消息的 Markdown DOM 节点数量是万级起步。

00:02，它刚开始查"还有哪些代码在 resize 时火上浇油"。

我取消了。

PC 拖窗口到今天还卡着。 这篇记录里这一行，就当欠条。

Safari 那次我停得心安理得：没有真机数据，猜着改只会更糟。这次不一样——它明明能修，是我不想在凌晨三点看它一条一条试。

两种停手长得很像，区别是：一种是有判断，一种是没耐心。

最后：vibe coding 教我的五件事

我在这 64 小时里学到的，没有一条是关于 React 的。

一、能把现象描述清楚，比能写代码更稀缺。

二、验收权比实现权重要。

三、"我不知道，但我能看出来不对"，是一种完整的能力。

四、能停手，也是能力。

五、但停手分两种。

如果重来一次，我会：报 bug 时把操作路径一步一步写出来。 提示词"失忆"那条，我写的是"修改-保存-更多操作-系统提示词，改成功了；开启新对话-更多操作-系统提示词，不见了"。它一眼定位到读的是另一层，不用猜。这不是技巧，是免费的精度。

折腾的乐趣大概就在这里——不是从零造一个，而是把别人搭好的房子，改到自己住着顺手。只不过这一次，我全程站在门口说"这儿再挪一点"，没有碰过一次砖。
